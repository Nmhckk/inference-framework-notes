# vLLM-Ascend GLM-5.3-Flash 非 PD 部署方案

状态：脚本已准备，服务器待晚间可用后验证。未操作 K8s。

## 目标

先用与 xLLM 相同的 32 个逻辑设备跑共置式非 PD：GLM-5.3-Flash W8A8、81920 输入、600 输出、48 请求、并发16、prefix cache 数据集。优先 4节点×TP8、DP4；若该镜像在 A3 上要求官方布局，则使用2节点×TP16、DP2，并把拓扑差异单独记录。

## 镜像选择

优先固定 `quay.io/ascend/vllm-ascend:v0.30.0rc1-a3`，适用于16逻辑设备的 A3/910C 节点。不要使用文档曾错误展开的 `v0.23.0-a3`：该版本没有 `Glm5Next*` 注册，见 [官方问题 #17951](https://github.com/vllm-project/vllm-ascend/issues/17951)。如果实机识别为 A2 风格8设备节点，改用 `quay.io/ascend/vllm-ascend:v0.30.0rc1`。

部署前必须用 `npu-smi info`、驱动版本、设备节点数和容器内 CANN 兼容性确定 A2/A3，不能只依据机器名称选择镜像。

## 时间估计

- 镜像与权重已在节点：容器和网络核查约10–20分钟；首次加载、编译、图捕获约15–30分钟；功能检查约10分钟。
- 镜像需要离线传入：总时间主要取决于镜像大小和堡垒机链路，通常再增加30–90分钟。
- 服务正常后完成一次48请求基准、日志收集和汇总约30–60分钟。

无依赖冲突时，拿到机器后约1–2小时可产出第一版数据。GLM-5.3-Flash 在 vLLM-Ascend 仍属实验支持，镜像/驱动不匹配或图捕获失败会延长时间。

## 启动顺序

1. 只读核查 NPU、驱动、HCCN、权重路径、镜像和端口；确认不是 K8s 进程后才清理旧测试容器。
2. 先单节点启动一个 TP8/TP16 实例，做短请求、8K和80K功能验证。
3. 启用 MTP3、Decode图、EP和prefix cache，检查输出、接受率与图命中。
4. 扩展为32设备 DP 服务；使用与 xLLM 完全相同的48条输入测试。
5. 保存服务端日志、AISBench JSON、每请求延迟、NPU利用率及失败记录。

参数化启动脚本见 [run_nonpd_rank.sh](run_nonpd_rank.sh)。该脚本在容器内运行，由环境变量选择 DP rank，不包含服务器地址和凭据。

## 公平比较门槛

- 相同权重目录及哈希；
- 总计32个逻辑设备；
- 相同的81920/600原始输入文件和随机种子；
- 相同48请求、并发16、request rate与prefix repeat配置；
- 同时报告 TTFT、TPOT/ITL、output throughput、成功率及 token/s/NPU；
- 分别保存默认配置和框架最佳配置，不能只比较单边调优结果。
